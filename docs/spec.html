01このアプリは何か

解こうとしている課題

大きな会社では、隣の部署に誰がいるか分からない。相談したい専門知識を持つ人が社内にいても、たどり着けない。同時に、社内での出会いは「言い出しにくい」という理由だけで機会が失われている。

この2つは「社内の人とつながりたいが、きっかけがない」という同じ課題の裏表です。だから1つのアプリで扱い、モードで完全に分離します。

想定利用者

誰何のために使うか
若手社員部署外に相談相手がほしい／社内に知り合いを増やしたい
中堅社員特定の技術・業務経験を持つ人を探したい
全社員趣味の合う人と社内でつながりたい

このアプリでしか成立しないこと

  • 相互オプトイン — 恋愛モードは、ONにした人同士にしか見えない。片方だけが見ることはできない
  • 片思いが漏れない — 両想いになるまで、相手には一切通知されない
  • 社内限定 — 会社のメールアドレスを持つ人だけが入れる、閉じた空間

02技術構成

層採用理由
フロントReact + Next.js (App Router)React 指定。Next.js は Vercel 製なのでデプロイ設定がほぼ不要
言語TypeScript型を先に決めれば、分担作業で画面がつながらない事故が減る
バックエンドNext.js の Route Handlers別サーバーを立てない。同じプロジェクト内に API を置ける
スタイルTailwind CSSCSSファイルを分けずに書けるので、分担時の衝突が起きにくい
データTypeScript のダミーデータDBなし。後述の差し替え設計で、あとから本物に交換できる形にする
インフラVercelGitHub と連携すると push で自動デプロイ
Vercel の一番おいしい機能

Pull Request を出すと、そのブランチ専用のURLが自動で発行されます（Preview Deployment）。

つまりリポジトリを clone していないメンバーも、URLを開くだけで動く画面を確認できます。「ここの文言おかしい」「この導線わかりにくい」をローカル環境なしでレビューできるので、コードを書かないメンバーが実質的に参加できる形になります。ここは意識的に使ってください。

Vercel の制約

サーバー側にデータを保存できません。Vercel の関数は実行ごとに使い捨てなので、ファイルに書き込んでも次のアクセスでは消えています。

今回は DB を使わないので、投稿・チャット・ハートなどの「書き込み」はすべてブラウザ側（React の state と localStorage）で保持します。リロードしても消えないようにするなら localStorage を使ってください。

032つのモードの設計

ここがこのアプリの核であり、同時に一番のリスクです。社内で恋愛の相手を探す機能は、設計を間違えるとハラスメントの装置になります。安全性の設計そのものが、このプロダクトの主張になります。

仕事モード

目的：業務で頼れる人・相談相手を見つける

見える相手：仕事モードをONにしている全員

表示項目：部署、担当業務、スキル、フリー欄

ハートの意味：「話してみたい」

恋愛モード

目的：社内での出会い

見える相手：恋愛モードをONにしている人だけ

表示項目：年齢、趣味、フリー欄（部署は任意で非表示可）

ハートの意味：「気になる」

安全性のための5つの仕様

#仕様なぜ必要か
1相互オプトイン恋愛モードをONにしていない人は、他人の恋愛プロフィールを見られないし、自分も表示されない。「見るだけ」ができない
2片思いは不可視ハートは相互一致するまで相手に通知されない。断られたことも、断ったことも発生しない
3同部署・上下関係の除外同じ部署／レポートラインの相手を表示しない設定。初期値はONにする
4ブロックブロックすると相互に一切表示されなくなる。理由の入力は不要
5匿名掲示板の「匿名」の定義表示が匿名なだけで、追跡不能ではない。内部には投稿者IDを保持する。この事実を利用時に明示する
実装上の注意

モードのON/OFF状態そのものを、他人から見えるようにしないでください。「あの人が恋愛モードをONにした」が分かる時点で、この設計は崩れます。一覧に出るかどうかだけで表現します。

画面設計の前提

デモはプロジェクタ投影です。文字を小さくしない、コントラストを落とさない、細い線を使わない。スマホ表示の対応は後回しで構いません。

06データモデル

この型定義を最初に確定させて main に入れてください。ここが固まっていないと、分担した画面がつながりません。

// lib/types.ts

export type Mode = "work" | "romance";

export type User = {
  id: string;
  name: string;
  avatarUrl: string;        // ダミー画像のURL
  department: string;       // 部署
  age: number;
  enabledModes: Mode[];     // 参加しているモード
  work: {                   // 仕事モードのプロフィール
    role: string;           // 担当業務
    skills: string[];
    bio: string;            // フリー欄
  };
  romance: {                // 恋愛モードのプロフィール
    hobbies: string[];
    bio: string;            // フリー欄
    hideDepartment: boolean;
  };
};

export type Like = {
  fromUserId: string;
  toUserId: string;
  mode: Mode;
  createdAt: string;
};

export type Match = {       // 相互ハートで成立
  id: string;
  userIds: [string, string];
  mode: Mode;
  createdAt: string;
};

export type Message = {
  id: string;
  matchId: string;
  senderId: string;
  body: string;
  createdAt: string;
};

export type Group = {
  id: string;
  name: string;
  hobby: string;
  memberIds: string[];
};

export type Post = {
  id: string;
  boardId: string;
  displayName: string;      // 「名無しの営業部」など自動生成
  authorId: string;         // 内部保持のみ。画面には絶対に出さない
  body: string;
  createdAt: string;
};

マッチ成立の判定

A が B にハート → Like を1件追加 → B から A への同じモードの Like が既にあるかを確認 → あれば Match を作成して通知。なければ何も起きず、B には何も伝わりません。

07ダミーデータの扱い

唯一のルール：画面から直接データを読まない

各画面は lib/data/users.ts を直接 import せず、必ず lib/repository.ts を経由してください。

// lib/repository.ts — データアクセスの唯一の入口

import { users } from "./data/users";

export async function getUsers(mode: Mode): Promise<User[]> {
  return users.filter((u) => u.enabledModes.includes(mode));
}

export async function getUser(id: string): Promise<User | null> {
  return users.find((u) => u.id === id) ?? null;
}

関数を async にしておくのがポイントです。あとで本物のDBに差し替えるとき、直すのはこのファイルだけで済み、画面側は1行も変わりません。

ダミーデータの量と質

ここで手を抜くとデモが死にます

「テスト太郎／テスト部」のようなデータでは、審査員に何も伝わりません。実在しそうな名前、実在しそうな部署、読んで面白いフリー欄が要ります。

目安は30人分。これはプロダクトの説得力を直接決める作業なので、コードを書かないメンバーの担当として最適です。掲示板の投稿文も同様です。

顔写真は、フリー素材か AI 生成のダミー画像を使ってください。実在の人物の写真は使わないこと。

09ブランチ計画

フェーズ0：先に1人で土台を作って main に入れる

ブランチやること
feat/setupNext.js の初期化、Tailwind 導入、lib/types.ts の確定、ダミーデータの雛形、共通レイアウトとヘッダー、Vercel との接続
順序を守ってください

これが main に入るまで、他のブランチを切らないこと。型定義とディレクトリが決まる前に各自が作り始めると、全員が同じファイルを作って必ず衝突します。

feat/dummy-dataダミーデータ30人分と掲示板の投稿文P0
docs/specこの仕様書の更新—

依存関係で気をつける点

  • feat/discover と feat/chat は Match 型を共有します。型は setup で確定済みなので、お互いのコードを待つ必要はありません
  • feat/dummy-data は lib/data/ しか触りません。他と衝突しないので、いつマージしても安全です
  • 各ブランチは1〜2日でマージ。長引かせないこと

10やらないこと

スコープ外を明示しておくことが、期間内に完成させる唯一の方法です。質問されたら「今回は対象外です」と即答してください。

やらないこと代わりにどうするか
本物の認証（SSO・メール認証）ダミーユーザーの一覧から選んでログイン
データベースTypeScript のダミーデータ＋ブラウザ側の state
画像アップロードダミー画像のURLを固定で持つ
リアルタイム通信チャットは送信したら自分の画面にだけ即反映
メール・プッシュ通知画面内のバッジ表示のみ
管理者機能・通報対応仕様として定義するが実装しない
スマホ対応の作り込みPC投影を優先。崩れない程度で十分
発表での言い方

やらなかったことは隠さず、「今回はここまで作り、次はここをやる」と明示してください。設計として理解した上で切ったことが伝われば、減点ではなく加点になります。

11デモの導線

5分の発表で見せる順番です。この流れが動くことが P0 の定義です。

#操作見せたいこと
1ログイン社内限定であること
2仕事モードで一覧を見る部署とスキルで人が探せる
3恋愛モードに切り替える配色と表示される人が丸ごと変わる。ここが山場
4ハートを押す相手には何も通知されないことを口頭で言う
5相互一致 → マッチ成立両想いになって初めてつながる
6チャットを開いて1通送るここまでが1つの体験として完結する
当日の保険

この6ステップを事前に画面録画しておいてください。会場のWi-Fiやデプロイの不調でライブデモが落ちた瞬間に、評価が消えます。録画があれば「では録画でご覧ください」で復帰できます。
