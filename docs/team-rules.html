チーム開発のルール

全員が同じリポジトリを触るので、最低限のルールだけ決めています。 覚えるのは下の3つだけ。あとはこのページを見ながらで大丈夫です。

1

main はいつでもデモできる状態に保つ

2

作業は必ずブランチで。main には直接 push しない

3

困ったら触る前に聞く。5分粘ったら手を挙げる

01作業を始めるとき

毎回この4行から始めてください。他の人の変更を自分のブランチに取り込む作業です。

git switch main
git pull
git switch feat/自分の担当
git merge main
これをやる理由

誰かが main にマージすると、自分のブランチは古いまま取り残されます。

放置するほど衝突が増えます。毎日やれば1〜2ファイル、3日ためると10ファイル同時に衝突します。

マージしても自分の作業は消えません。相手の変更が足されるだけです。

        自分の作業 ── 自分の作業 ── 合流
       /                          /
main ─●──────────────────────── 他の人のマージ

02コードを書いているとき

こまめに保存してください。何度やっても構いません。

git add .
git commit -m "何をしたか"
git push

push しても他の人には影響しません。自分のブランチに置かれるだけです。

03PR（プルリクエスト）を出す

粒度

1つの機能、または1つのバグ修正が終わったら出してください。細かめでOKです。

複数の機能をまとめて出さないこと。巨大なPRは誰もレビューできません。

  • タイトルは日本語で「何をしたか」（例：プロフィール詳細画面を追加）
  • 説明欄はテンプレートが自動で出るので、埋めるだけ
  • 未完成なら、タイトルの先頭に [WIP] と書く
出したら① Codex を呼ぶ

PR のコメント欄に、これをそのまま貼ってください。自動では動きません。

@codex review and write all review comments in Japanese

数分でレビューが返ってきます。日本語で返すよう指定してあります。指摘は重要なものだけなので、多くは出ません。

出したら② Slack で報告

「〇〇のPRを出しました。レビューお願いします」＋ PRのURL

GitHubの通知はすぐ埋もれます。Slackに流すところまでが1セットです。

PRを出したあとも push して構いません。PRの中身は自動で更新されます。作り直し不要です。

04レビューと承認

誰が何を見るか
Codexバグ・重大な問題。PRを出した人が自分で呼びます（前章のコメントを貼る）
開発系リーダー仕様と合っているか / 使いやすいか
禁止

自分のPRを自分で承認しないでください。

承認は開発系リーダーだけが行います。

承認を待っている間は、次の作業を進めてください。手を止めて待つ必要はありません。

05マージする

リーダーの承認をもらってから、PRを出した本人がマージします。

マージしたら必ず Slack で報告 ← 最重要

「feat/discover をマージしました。みんな main を取り込んでください」

この報告を見たら、全員がその場で 01 の4行を実行してください。後回しにするほど面倒になります。

マージが終わったPRのブランチは、GitHubの「Delete branch」ボタンで消してください。

06触らないファイル

原則触らない

次の4つは複数の人が同時に触ると必ず衝突します。

  • lib/types.ts
  • lib/repository.ts
  • components/Header.tsx
  • app/layout.tsx

触る必要が出たら、必ず Slack で呼びかけてから作業してください。

呼びかけは「lib/repository.ts 触ります」と書くだけです。これだけで事故が激減します。

07やってはいけないこと

禁止なぜ
git push --force他人の作業が消えます。絶対にやらない
git reset --hard自分の作業が消えます。自己判断で打たない
main に直接 pushデモが壊れます
他人のブランチに push相手が混乱します
.env をコミットAPIキーが流出します

08コンフリクトが起きたら

失敗ではありません。同じ場所を2人が変えたときに必ず起きるものです。

  • まず落ち着く。焦って操作しない
  • VS Code に「現在の変更を取り込む / 入力側の変更を取り込む / 両方の変更を取り込む」のボタンが出ます
  • どちらを残すか分からなければ、そのまま声をかけてください
やらないこと

自分の判断で相手の変更を消さない

ネットで見つけたコマンドを、意味が分からないまま実行しない

「壊したかも」と思ったら、何かする前に相談してください。push済みの内容はGitHubに残っているので、たいていは元に戻せます。

09発表3日前から

時期止めるもの通せるもの
3日前〜機能追加バグ修正のみ
前日〜バグ修正も原則停止致命的なものだけ（リーダー判断）
当日すべてなし

直前に入れた変更で壊れると、元に戻す時間がありません。「あと1つだけ」が一番危険です。

この期間は、デモの練習・画面録画・発表資料・バグ修正に使います。間に合わなかった機能は素直に切ってください。

10困ったときのコマンド

いま自分がどのブランチにいるか（VS Codeの左下にも出ています）

git branch --show-current

何を変更したか

git status

間違って main で作業してしまった（まだコミットしていなければ、変更を持ったまま移動できます）

git switch -c fix/作業中の内容

触る前に聞く。5分粘ったら手を挙げる。

一人で悩んでいる時間が、チーム全体で一番もったいない時間です。
「こんなことも分からないのか」と思う人はいません。聞いてください。
