01判断の前提となる3つの事実

① チャットに構造的にできないことは6つしかない

「Claude に資料のURLを投げるのと変わらない」を避けるには、この軸のどれかに乗る必要があります。2つ以上に乗れば、アプリである理由が立ちます。

軸中身
蓄積会話は忘れる。アプリは前回の結果を持ち続けられる
規模チャットは2〜3文書が限界。アプリは数十社×数年を回せる
スキーマ強制全社に同じ項目を埋めさせて、初めて「比較」が成立する
無人実行人がプロンプトを打たなくても始まる
決定的計算計算はコードでやる。LLMに算数をさせない
出典の追跡「どこに書いてあったか」を検証できる形で残す

② IRの「数字」はもう構造化されている

EDINET API では、有価証券報告書の XBRL が CSV に変換された状態で取得できます（type=5）。 売上・利益・セグメント別数値は、パースするだけで手に入ります。

ここが分岐点

つまり「AIに決算書を読ませて数字を出すアプリ」は、既に構造化されたデータをLLMで読み直しているだけになり、既存の財務データサービスと正面から競合します。

手が付いていないのはテキストです — 事業等のリスク、経営方針、対処すべき課題、MD&A。ここは XBRL でも数値化されず、既存ツールの検索軸にもなっていません。LLMを使う正当性があるのはこちら側です。

③ データ源はEDINETに限定する

データ源費用判断
EDINET API（金融庁）無料
要APIキー・電話番号認証		採用。有報・四半期報告書・XBRL が取れる
TDnet API（JPX）月24〜34万円規模除外。適時開示が必要でもEDINETで代替する
実装上の制約

EDINET API は実質3〜5秒に1リクエストまで。短時間に叩くと接続を切られます。本番デモでAPIを叩く設計にすると必ず落ちます。対象企業のデータは事前にローカルへキャッシュしてください。

02評価軸

5軸で評価します。各案に ●●●●○ の形で付けています（5段階）。

軸何を見るか
実装しやすさハッカソンの期間で動くところまで行けるか
デモ映え審査員に一言で伝わるか。画面で「おっ」となる瞬間があるか

この軸を入れた理由

「財務の学び」は、審査には一切効きません。それでも軸に入れているのは、チームの誰かにとってこのハッカソンが将来の資産になるかどうかが、賞と同じくらい大事だからです。ここを最初に言語化しておかないと、実装の都合だけで案が決まります。

03候補5案

A案

「言わなくなったこと」検出器

推奨・土台

同じ企業の有報を2期分つき合わせ、書き換えられた文言だけを抽出する

IR文書は前期のコピペが土台です。だからこそわざわざ書き換えた箇所には理由があります。リスク項目の新設、「成長」が「安定」に変わる、去年あった一文が消える。プロのアナリストが手作業でやっている読み方を自動化します。

チャット不可の理由
有報は数百ページ。2期分を入れても網羅的な差分は取れず、「見落としがない」ことを保証できない。それができるのはコードだけ
デモの見せ場
左右2画面で変更箇所をハイライト。右に「今年から言い始めたこと／言わなくなったこと」。消えた文言は人間もツールもまず気づかない
財務の学び
有報テキストの精読、開示制度の理解。「どの差分が重要か」の判断そのものがアナリストの訓練になる
強み
差分抽出はコードで確定的に取れる。LLMは差分の意味づけだけなので精度に依存せず、送るトークンも少なく安い。落ちにくい
伸ばし方
同業10社の同時期の差分を並べ、「業界全体でリスク認識が動いた」を見せる

D案

中期経営計画の「有言実行度」スコア

推奨・学び最大

過去に掲げた数値目標を抽出し、実績と突き合わせて達成率を出す

「売上1兆円」「ROE 10%」といった目標をテキストから抽出し、該当年度の実績（XBRL）と機械的に照合します。出力は一言で伝わります — この会社は、言ったことをやるのか。

チャット不可の理由
複数年度の文書横断＋数値照合。目標はテキスト、実績はXBRLという異種データの突き合わせが必要
デモの見せ場
「この会社は過去5回の中計で目標を1回しか達成していない」。説明が要らない
財務の学び
5案で最も濃い。経営計画の読み方、KPIの設計、目標の信頼性評価。運用や与信の現場でそのまま使う視点
AIの必然性
目標値は表記が企業ごとにバラバラ（「1兆円」「10,000億円」「対前期比+20%」）。非定型テキストの正規化はLLMが最も効く仕事
最大のリスク
中期経営計画は有報ではなく決算説明資料やIRサイトにあることが多い。有報の「経営方針、経営環境及び対処すべき課題等」に数値目標が載っている企業もあるが、載っていない企業もある。着手前に5社ほどで実地確認が必要

E案

財務三表シミュレーター

条件を動かすとPL・BS・CFが連動して動く。黒字倒産を体験する

「売掛金の回収が30日遅れたら」「在庫を1.5倍持ったら」をスライダーで動かすと、三表が連動して再計算されます。利益は黒字なのに現金が枯れていくのを目で見られる。

チャット不可の理由
インタラクティブな即時再計算。計算はコードでやるので数字が常に正しい
デモの見せ場
スライダーを動かすと現金残高がゼロを割る瞬間。会場が静かになるタイプの見せ場
財務の学び
三表連動は財務職の基礎中の基礎で、かつ多くの人が体で理解していない領域。作った本人が一番学ぶ
弱点
AIを使う理由がほぼない。AIハッカソンなら不利。実企業の有報から初期値を読み込む部分と、「なぜこうなるか」の解説生成にLLMを噛ませて補強する必要がある

単独で全部が高い案はありません。A はどの軸も安全側だが突き抜けない。D と E は学びとデモが最高だが、それぞれデータ確実性とAI必然性という別々の穴を持っています。

だから提案は「A を土台にして D を載せる」です。A の差分エンジン（企業の言葉を時系列で追う仕組み）は、そのまま D の「目標値の変化を追う」機能に使えます。作るものは1つ、見せ方が2つ。A が動けば最低限の成果は確保され、D まで届けばデモが強くなります。

06見送った案と、その理由

案見送る理由
粉飾・異常検知実在企業を「疑いあり」と表示するのは名誉毀損のリスクがあり、審査でも必ず突かれます。過去に確定した事例だけを扱う教育用ツールに限定すれば成立しますが、その形だとデモのインパクトが落ちます
セグメント構造のSankey図見た目は強いが、XBRLだけで作れてLLMを使う理由がない。差別化にならない
経営者トーンのスコア化グラフは映えるが主観指標なので根拠を突かれると弱い。審査で狙われる形
新着開示の監視→Slack通知最も「アプリらしい」が、ライブデモで何も起きない。A案のおまけ機能として「差分が出たら通知」なら成立
個人投資家向け「わかる化」技術的な新しさは薄い。ただし文系メンバーが主役になれるので、チーム構成を活かす方向に振るなら再検討の価値あり

07会議での決め方

多数決にしないでください。好みの言い合いになり、決まっても誰も納得しません。評価軸を埋める作業にします。

時間やること
5分この資料の 01「判断の前提」 だけ読み合わせる。ここが共有できていないと議論が噛み合わない
15分各案について「これを1週間後にデモしている自分」を想像して、引っかかる点を出す
10分5軸のうち、今回のチームが何を優先するかを決める。案を選ぶ前に軸の優先順位を決めるのが肝
10分案を1つ決める。決まった瞬間に Notion のカードにする
10分役割分担。その場で担当者名をカードに入れる
10分次回日程を決めてカレンダー登録。D案が候補に残るなら「5社で中計の所在を確認する」タスクを誰かに割る
Google Meet の制約

無料アカウントは3人以上の会議が60分で自動終了します（残り15分からカウントダウン表示）。切れても同じURLで入り直せばまた60分使えますが、再入室に数分かかります。上の配分は60分ぴったりなので、最後の2項目を先にやってしまうほうが安全です。

08案が決まる前に着手できること

どの案になっても無駄にならない作業です。会議を待たずに進めてください。

やることなぜ今か
EDINET の APIキー登録電話番号認証があるので即日終わらない可能性がある。全案の前提
有報1社分を手で取得してみるデータの形を1度見ておくと、会議での議論の解像度が上がる
対象企業を5社選ぶ「変化が起きている会社」を選べるかが、A案・D案の成否を分ける
中計の所在確認（D案が残るなら）有報に数値目標が載っているか。ここが崩れるとD案は成立しない
全員の環境構築案とは無関係に必須。手順書は docs/setup-guide.html

この資料は決定事項ではなく、会議で比べるための材料です。評価の点数は作成時点の見立てなので、実地確認の結果が出たら書き換えてください。
